# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working in this repository.

## Commands

Local dev:

```sh
go install ./cmd/ccdash      # places ~/go/bin/ccdash with Version="dev"
go build ./...               # any package
go test ./...                # transcript / wrapper / redact have unit tests
go vet ./...                 # CI runs this on every push
```

Run:

```sh
ccdash install-hooks         # one-time: writes hook entries into ~/.claude/settings.json (+ the hook.sh forwarder)
ccdash                       # opens the TUI; embeds the collector for the session
ccdash -k                    # spawns a detached collector, then opens the TUI
ccdash --group home-lab        # locks the TUI to a single project / user-named group
ccdash --version             # prints the build-time main.Version
ccdash update                # self-update from the latest GitHub release
ccdash server --listen 0.0.0.0:9123   # opt-in: bind beyond loopback for remote mode
ccdash remote set --url http://host:9123 --token-file ~/.ccdash-token   # one-time client config (~/.config/ccdash/config.json)
ccdash -r                    # TUI against the configured remote collector (--remote-url overrides ad hoc)
ccdash hub serve --no-auth --listen 127.0.0.1:8080   # local dev hub (real deployments use OIDC; see README "Hub mode")
ccdash hub join --url http://127.0.0.1:8080          # device side: paste the token from the portal's "Add device"
```

To test hub mode without touching your real collector or `~/.claude/settings.json`, run the device collector with `HOME`, `XDG_STATE_HOME` and `XDG_CONFIG_HOME` pointed at a temp dir and `ccdash server --listen 127.0.0.1:<other port>` (a fresh state dir has a new token; with your real HOME, `syncInstalledHooks` would rewrite settings.json to it).

CI (`.github/workflows/ci.yml`) runs `go vet`, `go test`, `go build` on every push / PR. The `release.yml` workflow fires on `v*` tag pushes and produces 4 binaries (linux/darwin × amd64/arm64) plus sha256 sidecars. Tags can be cut from the GitHub UI via the manual `tag` workflow.

## Architecture

ccdash is a single Go binary that plays three roles depending on how it's invoked:

1. **Collector** — an HTTP server bound to `127.0.0.1:9123` that receives Claude Code's hook events, writes them to SQLite, and (optionally) blocks PermissionRequest hooks waiting for an operator decision.
2. **Discoverer** — a goroutine that polls `~/.claude/sessions/<pid>.json` and `~/.claude/projects/*/<id>.jsonl` every ~10 s to surface idle/stopped sessions even when no hook has fired.
3. **TUI** — a Bubble Tea v2 application that reads the SQLite store, tails transcripts on disk, mirrors server-hosted claude sessions live in the right pane, and dispatches per-session actions (attach, approve, generate titles, projects).

The TUI auto-spawns the collector when none is listening, and tears it down on quit. `-k` and `ccdash server` cover persistent-collector setups.

A fourth, optional role is the **hub** (`ccdash hub serve`, `internal/hub`): a web portal on a home server. Joined devices' collectors dial out to it over a WebSocket + yamux tunnel (`internal/tunnel`) and the hub forwards browser requests through it. See `docs/decisions/0003-hub-web-portal.md`.

### Data flow

1. Claude Code fires a hook that lands on `http://127.0.0.1:9123/hooks/<event>`. PermissionRequest is a blocking HTTP hook; every other event is a `command` hook running `$XDG_STATE_HOME/ccdash/hook.sh <endpoint>`, which drains stdin and backgrounds a `curl` POST so a stopped or hung collector never stalls the session. Either way the request carries `X-Ccdash-Token` (auth; hook.sh reads the token file at run time), `X-Ccdash-Managed: true`, and several `X-Ccdash-*` env-var values.
2. `internal/server` runs the request through rate-limit → token check → handler. Handlers run `redact.JSON` / `redact.String` over the payload before persisting.
3. `internal/db` writes a row in `events`. SessionStart also `UpsertSession`; PermissionRequest also `InsertApproval` (status = pending).
4. The TUI polls SQLite on a ticker (default 1 s) via `internal/db.ListSessions` and `ListPendingApprovals`. The right pane separately tail-reads the selected session's transcript JSONL via `transcript.LoadTail` so updates land within the same tick.
5. PermissionRequest is the one handler that *blocks*. It opens a Go channel, registers it in `Server.pending[id]`, and selects on `<-ch | timeout(25 s) | r.Context().Done()`. The TUI's `decideApproval` POSTs to `/approvals/<id>/decide`, which routes through the channel back to the blocked goroutine, which then writes the appropriate `hookSpecificOutput` JSON so Claude obeys.

### Settings page (`,`)

`internal/settings/AllSpecs()` is the single source of truth for the list of preferences. Adding a setting means:

1. Add the storage field on `settings.Settings` and a default in `Defaults()`.
2. Pick a `Kind` (`KindBool` / `KindInt` / `KindEnum` / `KindString` / `KindAction`) and append a `Spec` to `AllSpecs()`.
3. Add a `loadPairs` entry (the read path) and the typed accessor branch in `Get` and `Set`. `AllKeys()` — which feeds `GET /api/settings` for remote mode — derives from `AllSpecs` automatically, and `TestKeyTablesAgree` fails if `loadPairs` and `AllSpecs` ever drift apart.
4. If the value gates a TUI behavior, read it from `m.settings.Foo` rather than caching on the model — the settings page mutates `m.settings` in-place via `settings.Set`.

The TUI render layer dispatches on `Spec.Kind` automatically; you don't normally need to touch `internal/tui/tui.go` to add a new pref.

### Key invariants and behaviors

- **127.0.0.1 is the default, not a hardcoded ceiling — but hooks ALWAYS arrive via loopback.** The embedded/managed collector (plain `ccdash`, `-k`) always binds `internal/paths.DefaultHost` — no flag changes that path. A standalone `ccdash server --listen <addr>` can opt into a non-loopback bind for remote mode (`internal/cli.checkBindSafety` treats empty/wildcard hosts as non-loopback, logs a warning, and refuses to start without an existing token). Because `install-hooks` bakes `127.0.0.1:<port>` into settings.json and `store.Local.DecideApproval` targets the same address, `server.listenAddrs` adds a second `127.0.0.1:<port>` listener whenever the bind host is a specific non-loopback address — never remove it, or every hook on the collector's own host gets connection-refused. Wildcard binds (`:9123`, `0.0.0.0`, `::`) already accept loopback and stay single-listener. Every request, loopback or not, still needs `X-Ccdash-Token`. `--addr` is a deprecated alias for `--listen`. See "Remote mode" in the README and the Store seam note below.
- **The Store seam (`internal/store`) is what makes remote mode possible.** `internal/tui` and the plain-text `internal/cli` subcommands (sessions/approvals) talk to a `store.Store` interface, never to `*db.DB` or the filesystem directly. `store.Local` wraps `*db.DB` + direct file reads + `internal/summarize` (titles), preserving pre-remote-mode behavior exactly (including running `DecideApproval` over HTTP to the collector's own `/approvals/{id}/decide` — the pending PermissionRequest hold lives in `Server.pending`, a channel in the collector's memory, not in SQLite, so even Local can't just write the DB). `store.Remote` talks the same shape of operations to `internal/server`'s `/api/...` routes. `internal/server` itself is NOT part of this seam — it keeps working directly against `*db.DB` internally; only the client side goes through `store.Store`. When adding a TUI/CLI capability that reads or mutates session data, add it to the `Store` interface (both impls) rather than reaching for `*db.DB` from `internal/tui` or `internal/cli` again.
- **`statusLine` is wrapped, not replaced** (`internal/hookcfg/statusline.go`). `install-hooks` / `install-statusline` point it at `$XDG_STATE_HOME/ccdash/statusline.sh` (recognised by the `ccdash/statusline.sh` path), which backgrounds a POST of Claude Code's status JSON to `/hooks/statusline` and then runs the operator's original command (embedded in the script; the original setting object lives in `statusline.orig.json` for `uninstall-*`). The collector keeps the latest JSON per session in memory (`GET /api/sessions/{id}/statusline`, not rate-limited — it never touches SQLite) and the portal's chat status line draws from it (schema: code.claude.com/docs/en/statusline), falling back to the transcript-derived usage line.
- **Hook entries belong to ccdash via the `X-Ccdash-Managed: true` header (HTTP entries) or a command containing `ccdash/hook.sh` (forwarder entries).** `install-hooks` and `uninstall-hooks` use `isManagedEntry` to round-trip our entries without disturbing the operator's other hooks. Don't touch hook entries that match neither. Only PermissionRequest may stay a blocking HTTP hook — it's the one event whose response Claude consumes; anything new that is fire-and-forget goes through the forwarder.
- **The auth token rotates only when the file is missing.** On first start `auth.LoadOrCreate` writes a fresh 32 B hex token to `$XDG_STATE_HOME/ccdash/token` (mode 0600). `server.syncInstalledHooks()` re-runs `install-hooks` on boot when the token in `settings.json` doesn't match, or when `hookcfg.NeedsResync` sees a pre-forwarder layout / missing `hook.sh` — but only if `auto_install_sync` is on and there are existing hook entries to update.
- **The DB is never reset by code.** `migrate()` is `CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ADD COLUMN` only; ignore `duplicate column` errors. Operators can hand-delete `~/.local/state/ccdash/ccdash.sqlite` to start over.
- **`s.UserGroup` wins over `s.Repo` for grouping.** `groupOf(s)` consults `UserGroup` first, then `Repo`, then `filepath.Base(s.Cwd)`. The tab strip (the UI rendering of groups) dedupes auto-derived entries against user-named ones, so an operator naming a group the same as a repo just merges them.
- **`s.Title` is the auto-derived first user prompt; `s.GenTitle` is the `claude -p` generated one (ctrl+t); `s.CustomTitle` is the operator override.** Precedence is CustomTitle > GenTitle > Title, and `Session.DisplayTitle()` centralizes it — never rebuild this logic in a render path. `s.Num` is the short sequential "#N" handle (`Session.Ref()`): assigned at insert as `MAX(num)+1` inside the upsert, backfilled in first-seen order by `db.backfillNums`, unique-indexed — never renumber existing rows. Title generation (`summarize.KickoffTitles`) batches up to `MaxTitleBatch` sessions into ONE `claude -p` call keyed by Num and shares the summary's gate, isolation and marker. The transcript-derived title gets `redact.String` applied before persistence so a prompt containing an API key doesn't show up in the list.
- **`internal/transcript.LoadTail` exists for a reason.** The asmr-palyer transcript in this dev environment is ~30 MB; doing a full `Load` on every tab change made selection feel laggy. Use LoadTail for live-tail surfaces; reserve full `Load` for the modal viewer (`o`).
- **`claude -p` spawns are isolated.** `summarize.RunTitles` invokes claude with `--setting-sources project` and cwd `/tmp` so the title subprocess does NOT inherit our hooks (otherwise it would loop back to our collector and pollute the session list). The prompt is also prefixed with `summarize.Marker` (still `[ccdash:summary]`) and `discovery.Scan` skips any transcript whose first user prompt starts with that marker.
- **Approvals fall back from `tool_use_id` to oldest-pending.** PermissionRequest payloads don't include a `tool_use_id`, so PostToolUse handlers call `ResolveOldestPendingForTool` after `ResolvePendingByToolUseID`. The discovery loop also sweeps anything pending > 45 s into `timeout`. Don't rely on tool_use_id alone.
- **Secure-mode toggles are explicit.** `approve_enabled`, `summary_enabled` (now gates only `claude -p` title generation), `attach_enabled`, `auto_install_sync`, `hub_enabled` each turn off one risk-bearing capability; the "Apply secure preset" action flips all five. The TUI keys for these features check the flag and flash "<feature> is OFF" when disabled — don't bypass.
- **Mouse wheel zoning is layout-aware.** `mouseInRightPane` re-derives geometry per-event because vertical layout splits Y instead of X. Auto-vertical decides via `m.width < settings.VerticalAutoCols`.
- **`groupLocked` (from `--group`) hides the strip and disables h/l/Tab/Shift+Tab.** It also keeps `archiveCurrentGroup` from auto-advancing past the locked group. The deprecated `--tab` alias is still accepted (hidden) so existing scripts don't break.
- **The right pane is a live terminal for server-hosted sessions.** Every PTY the server spawns (`POST /pty/start`) is wrapped in a `charmbracelet/x/vt` emulator (`internal/server/screen.go`) that consumes the child's output whether or not anyone is watching. The TUI subscribes via `GET /pty/{key}/screen` (HTTP upgrade → newline-delimited JSON, types in `internal/screen`) and splices the rendered rows into the right pane (`internal/tui/live.go`). `syncLive` runs after every `Update` and owns connect / resize / teardown; don't dial the stream anywhere else. `desiredLiveKey` decides which sessions qualify: sessionID (registered alias) or `pid-<N>` (fresh `n` spawn) present in the `GET /pty` list. A fresh `n` spawn is keyed `pid-<shell pid>`, which never equals claude's own PID (it runs under `$SHELL -i -c`), so the server aliases it to the session ID two ways: `handlePTYStart` hands each child a hook tag (≥ `ptyTagBase`) in `CCDASH_WRAPPER_PID` that `ensureSession` matches when the child's first hook reports it as `X-Ccdash-Wrapper-Pid`, and — for machines without ccdash hooks — the discovery loop's `aliasPTYsByParent` matches a claude from `~/.claude/sessions` whose parent PID is the PTY's shell. Meanwhile the TUI shows a placeholder row keyed by the PTY (`injectSpawnRow`) so the new claude is mirrored and typeable before its first prompt creates a transcript; `selectSpawned` swaps to the real row (by the alias seen in `GET /pty`, or by `WrapperPID`) when discovery lists it. Sessions started outside ccdash cannot be mirrored and keep the transcript tail.
- **The real terminal cursor is the IME anchor.** `View()` returns `tea.View` (Bubble Tea v2) and sets `Cursor` to the emulator cursor only while the live pane has focus (`liveCursor`). Never draw a fake cursor cell instead — that's what broke IME composition in v0.3.x (see `docs/decisions/0002-live-right-pane.md`). Everything that computes pane geometry (`rightPaneGeom`, `liveScreenGeom`, `mouseInRightPane`) must go through `bodyLayout` so the cursor lands on the cell the renderer drew.
- **Fullscreen attach (`F`) rides the same PTY.** `attach.StreamClient` + `tea.Exec` relays raw bytes via `/pty/{key}/stream`. While a raw client is connected the emulator keeps consuming output but `responsePump` drops its DSR/DA replies so the operator's terminal is the only responder. On return, `attachDoneMsg` zeroes `sentCols/sentRows` so `syncLive` pushes the pane geometry back. `Ctrl+D` (`attach.EscapeByte`) detaches without killing the child; in the live pane `Ctrl+]` / `Ctrl+D` do the same hand-back.
- **Bubble Tea v2 conventions.** Imports are `charm.land/bubbletea/v2`; key handlers take `tea.KeyPressMsg` and test `msg.Code` / `msg.Text` / `msg.String()` (space is `"space"`, not `" "`); mouse handlers take `tea.MouseWheelMsg` / `tea.MouseClickMsg`. Alt-screen and mouse mode are declared on the `tea.View`, not `NewProgram`. The approval bell is written to stdout by `ringBellCmd` because the cell renderer strips control characters from view content.
- **`x/vt` is pinned to a commit** (pre-v1, untagged). Bumping it is a deliberate change: re-run the manual IME check in `docs/decisions/0002-live-right-pane.md` afterwards. `cmd/vtspike` is the standalone harness for that check.
- **Child output is scrubbed before it reaches the emulator.** x/ansi treats 0x9C as the C1 String Terminator even inside an OSC, but it's a UTF-8 continuation byte — Claude Code's `✳ <summary>` window title (✳ = E2 9C B3) used to spill onto the screen every spinner frame. `strFilter` (`internal/server/strfilter.go`) drops non-ASCII bytes inside OSC/DCS/APC/PM/SOS payloads; the raw fullscreen relay stays unfiltered. Likewise `normalizeKey` rewrites Shift/lock-modified text keys to plain presses because x/vt's encoder silently drops any printable key with `Mod != 0`. Keep both until upstream fixes them. For new rendering bugs, start the collector with `CCDASH_PTY_TRACE_DIR=<dir>` to dump each PTY's raw output to `<dir>/<key>-<unix>.raw` and replay it.

- **Hub tunnel requests are authorized by the device-side allowlist, not the loopback token.** `Server.hubLoop` (started from `ListenAndServe`, so the embedded collector joins too) re-reads `hubcfg` and `hub_enabled` on every attempt; `hubHandler` checks `hubAllowed` against the device's own settings and only then injects `X-Ccdash-Token` and calls the mux. Never add hook routes, `/shutdown` or settings writes to that allowlist — the point is that a compromised hub can't flip the device's toggles. A new portal capability that touches device data gets an explicit allowlist entry (and its gate) plus a case in `TestHubAllowed`.
- **The portal's chat view types through `POST /pty/{key}/input`, not the raw stream.** The raw `/pty/{key}/stream` is single-client (409), so the chat must not depend on it; input writes straight to the PTY (bracketed paste for multi-line text, then `\r` after a short pause). TUI-only prompts are read from the emulator via `GET /pty/{key}/text` and detected client-side (`screenPrompt` in `web/app.js`: a `❯` cursor on a numbered or sibling-aligned list). The xterm.js view is the hub bridging a browser WebSocket to the raw stream.
- **Portal images and questions.** `POST /hub/upload` (device side, attach-gated, images only, 20 MB, 0600 under `$XDG_STATE_HOME/ccdash/uploads`, 7-day sweep) returns a path the chat pastes with `input {paste:true}` — Claude Code turns a pasted image path into `[Image #N]`. AskUserQuestion is NOT in the transcript until answered, so the pending form is parsed off the emulator screen (`screenAsk` in `web/app.js`) and answered with the keys a person would press (digit = pick/toggle, `→` = next for multi-select, Type-something digit + paste + Enter, `1` on the review step); the answered card comes from `toolUseResult.answers`. If Claude Code's dialog layout changes, `screenAsk` is what breaks.
- **Restarts keep the hosted sessions** (`internal/server/restart.go`). `POST /pty/{key}/restart` kills one hosted claude and starts `claude --resume` under the same key (409 for a `pid-*` PTY with no session yet). `POST /api/restart` (attach-gated on the hub allowlist) and `/shutdown?resume=1` (the TUI's "Restart ccdash") write the hosted sessions to `$XDG_STATE_HOME/ccdash/resume-on-start.json`; the next collector start resumes them once and ignores a file older than 10 min, so a later reboot never auto-launches claude. `/api/restart` re-execs only under `ccdash server` (`Server.CanRestart`; `ListenAndServe` returns `server.ErrRestart`), else 501.
- **Session colors** come from `model.Session.Color()`: the `color` column — filled for running (active/idle) sessions by `db.AssignRunningColors` (discovery tick) with `model.PickColor`, which draws the color farthest (hue + lightness) from the other running sessions'; `SetColor(id, "random")` re-rolls by the same rule — else `SessionPalette[(Num*7) % 24]` (consecutive `#N` never collide), else an FNV-1a hash of the session ID. The portal's `SESSION_PALETTE` / `sessionColorOf` in `web/app.js` must stay identical (same order, same stride) — `TestColorStable` pins sample values. The TUI draws the bar as a background-colored space (block glyphs are East-Asian ambiguous).
- **Projects are operator-named session sets, separate from groups** (`sessions.project` + `projects` table: name, color, created_at, ord). `p` sets/clears (`Store.SetProject`; `db.ensureProject` gives a new project a color via `model.PickColor` away from the other projects'), `P` re-rolls (`Store.SetProjectColor(name, "random")`). Routes: `POST /api/sessions/{id}/project {"project"}`, `POST /api/projects/color {"project","color": "#rrggbb"|"random"}`, `POST /api/projects/rename {"from","to"}` (merges onto an existing name) — all on the hub allowlist via `hubSessionEdit`; `GET /api/projects` is a hub read route. `projectsFirst` moves members to the newest end of the list (top, or bottom with newest_at_bottom), one block per project in `projects.ord` order (operator-set via `[`/`]`, portal ▲▼, MCP `order_projects`, `POST /api/projects/order`; a new project takes MIN(ord)-1 = newest end; activity never reorders projects, and members sort by first_seen), headed by a full-width band (`renderProjectHeader`) and each row carrying a one-cell project-color gutter — independent of the date buckets. Color fallback is `model.ProjectColorOf(name, stored)` (FNV-1a of the name into `SessionPalette`), mirrored by `projectColorOf` in `web/app.js` — keep them identical; `model.InkOn` picks black/white text for a band.
- **"Favorite" is shown as "pin"** (the `favorite` column / API / `Session.Favorite` keep their names). `db.SetFavorite` stamps `favorite_at` (Unix ms) → `Session.PinnedAt`; pins sort most recently pinned first — `ListSessions` ORDER BY for the Pinned bucket, `projectsFirst` / `projectsFirst` (app.js) put pins at the top of their project block. Activity never reorders pins.
- **Automatic titles** (`internal/server/autotitle.go`): discovery counts typed prompts per transcript (`discovery.countPrompts`, incremental by offset, capped at `PromptCap` = 2) and `maybeAutoTitle` (discovery tick, ≤ 1 kickoff/min) batches sessions with no gen/custom title and an empty `title_status`, active in the last 24 h, that have 2 prompts or 1 prompt + 2 min quiet, into `summarize.KickoffTitles`. Gated by `auto_title` AND `summary_enabled`. Never retries: any `title_status` (running/done/error) excludes the row.
- **`n` inside a project** pre-fills the picker with `projectDir` (the project's most recent session cwd) and sends `project` in `POST /pty/start`; the server keeps it on the `ptyEntry` and `applyPTYProjects` (discovery tick) assigns it once the PTY has a session-ID alias and a row — never overriding a project the session already has. The portal's project-band ＋ passes the same field.
- **`ccdash mcp`** (`internal/mcpserver`) is a hand-rolled stdio MCP server (newline JSON-RPC: initialize / ping / tools/list / tools/call) over `store.Store`, so `-r` works. Read tools (`overview`, `list_projects`, `list_sessions`, `get_session`) plus organizing tools (`set_project`, `order_projects`, `rename_project` — renaming onto an existing name merges via `db.RenameProject`, `set_project_color`, `set_title`, `set_archived`); `--read-only` drops the latter. Don't add tools that start / stop claude or answer approvals. stdout is the protocol, so nothing else may print there.
- **Project picker candidates come from `GET /api/projects`** (`db.ListProjects`: the projects table, so projects whose sessions are all archived still show). In the TUI an empty `p` input is "no change"; removal is the explicit `removeProjectLabel` entry — don't make an empty enter remove again.
- **Auto-archive is once per local day and reversible only for its own rows** (`internal/server/autoarchive.go`, `db.AutoArchive`). `maybeAutoArchive` runs on the discovery tick, skips when `auto_archive_days` = 0 or the settings key `auto_archive_last` already holds today's date, and archives sessions with `last_seen` older than N days — never pinned (favorite) sessions, project members or active/idle sessions — setting `auto_archived=1`. `UpsertSession` / `TouchSession` unarchive only `auto_archived` rows when the session comes back (active/idle or newer `last_seen`); a manual `x` (`SetArchived`) clears `auto_archived`, so it is never undone automatically.
- **The footer always ends with `? help  q quit`.** `fitKeys` (`internal/tui/help.go`) trims from the middle on narrow terminals; the full key list lives in `helpSections` (rendered by `helpLines` as the `?` window) — add new keys there, and to the footer only if they're common.
- **Hub push notifications poll devices through the tunnel** (`internal/hub/notify.go`, `watchDevice` per connected device, 4 s) and fire on changes of each session's `attention` (see below) — needs_you and done — naming the tool for pending approvals. The first poll is a baseline; a per-key cooldown dedups. The same poll keeps the per-device snapshot behind `GET /api/board`. Device-side additions the portal uses: `GET /hub/settings` (read-only view; settings writes stay off the allowlist), `GET /hub/skills`, and `POST /api/titles` (summary_enabled is enforced inside `summarize.KickoffTitles`).
- **Subagents live in their own files.** `<transcript without .jsonl>/subagents/agent-<id>.jsonl` (+ `.meta.json`: type, description, parent `toolUseId`, `requestShape`). A running subagent is not in the parent transcript yet, so the portal reads `GET /hub/subagents?session=` (status from the tail: `SubagentHandback` = done, quiet > 10 min = stale) and `GET /hub/subagents/{session}/{agentId}` (tail, path derived from the DB row — never from the request).
- **Attention is collector-side state on the session row** (`attention`, `attention_reason`, `attention_at`; `internal/server/attention.go`). needs_you ← PreToolUse of AskUserQuestion / ExitPlanMode (cleared by their PostToolUse), permission Notification hooks, and `attentionLoop` reading hosted PTY screens through `internal/screenprompt` (the Go twin of `screenAsk`/`screenPrompt` in `web/app.js`); pending approvals are folded in at read time (`db.finishAttention`). done ← Stop; cleared by `POST /api/sessions/{id}/seen` (`Store.MarkSeen`: TUI selection, portal chat open) or the next prompt. The hub's push notifications and `/api/board` only read this field — add new "needs you" signals here, not in the hub.
- **Portal diff review and usage are read-only device routes.** `GET /hub/git/status|diff?session=` run `git` with `GIT_OPTIONAL_LOCKS=0` in the session's DB cwd (paths confined to the repo). `internal/usage` totals transcript `message.usage` (deduped by message id, incremental per file, subagent files included) at API list prices — an estimate, labelled as such; prices live in `usage.prices`.
- **Hub auth:** OIDC (any issuer; in the home lab Cloudflare Access for SaaS) + `AllowedEmails` (the hub refuses to start without one) + HMAC-signed cookies keyed by a secret in hub.sqlite; or `--tailscale-auth` (loopback listen only) trusting `tailscale serve`'s `Tailscale-User-Login` header against the same list. The SPA polls `/api/me` and reloads when the embedded-assets hash changes. `--no-auth` is refused on a non-loopback listen. Mutating `/api/` calls go through `http.CrossOriginProtection`; the terminal WebSocket relies on coder/websocket's same-origin check — keep both.
- **Hub read tokens** (`internal/hub/readtoken.go`, `docs/decisions/0004-hub-read-tokens.md`): `CCDASH_HUB_READ_TOKENS` / `--read-token-file` give machine clients `Authorization: Bearer` access to GET-only `readTokenRoutes` (board, active, devices, a device's sessions, transcript tail). `apiAuth` takes the bearer branch only when tokens are configured; any other route or method is 403, a cookie on a bearer request is dropped. Widening `readTokenRoutes` widens every token — add a case to `readtoken_test.go`. The collector's transcript tail also takes `?lines=N`.

### Common gotchas

- **East Asian Width.** The terminal box-drawing `─` is "ambiguous" — runewidth says 2 cols on CJK locales, but many terminals draw it as 1. The vertical-layout body separator uses ASCII `-` for that reason; the header rule still uses `─` because it's followed by a known-width header bar. If you add a new full-width rule, mirror the ASCII-fallback pattern.
- **lipgloss column widths and styled strings.** `fmt.Sprintf("%-18s", styledStr)` doesn't work — `%-18s` counts ANSI escape bytes too. Pad first, style after; or use `runewidth.FillRight` against the unstyled version.
- **Bubble Tea + writes to stderr.** During alt-screen rendering, writes to stderr corrupt the buffer. The collector's `log.Printf` output is redirected via `cli.redirectLog()` to `~/.local/state/ccdash/ccdash.log` whenever the TUI embeds it. Don't add stray `fmt.Fprintln(os.Stderr, ...)` calls inside the TUI's lifetime.
- **ALTER TABLE migration ordering.** Append new ALTERs to the slice in `db.migrate`. Don't re-order the existing ones — every existing user has a partially-migrated DB already and the order matters for legacy fields like `layout_vertical` / `layout_auto` whose values are folded into `layout_mode` on Load.
- **macOS BSD sed.** `install.sh` runs on user shells; it must work on BSD sed (no `\+`, no `-i ''` quirks). Test with `sh install.sh` and ideally also against macOS BSD utils before shipping.
- **GitHub API rate limit (60/hr unauth, per source IP).** Behind a shared NAT the anonymous budget is usually spent by someone else, so `selfupdate` authenticates API calls with `CCDASH_GITHUB_TOKEN` / `GITHUB_TOKEN` / `GH_TOKEN` / `gh auth token` (first found; api.github.com only — never asset downloads), and `install.sh` does the same with `GITHUB_TOKEN` / `GH_TOKEN` / `gh`. 403s still carry the rate-limit hint; `CCDASH_VERSION=v0.1.x` remains the install-script escape hatch.
- **Unsupported OS / arch.** Only linux/darwin × amd64/arm64 are released. Windows is not on the roadmap.
